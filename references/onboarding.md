# 首次使用与续办

目标：让用户知道怎么使用，建立可验证的远端与日历连接，然后完成一个真实但小范围的计划闭环。已有资料先读进度再续办，不重新盘问。

## 开场介绍

用简短自然语言介绍：

> 我可以把长期目标拆成阶段和每日行动，安排到日历，记录完成、延期和备注，再给出复盘建议。资料存放在你指定 Git 仓库的 plans/，可以和 Atlas 等个人 Skill 共用仓库。你可以随时修改、跳过或指定不保存。提醒需要日历通知或能定时运行的 Agent；仅安装技能不会自动后台提醒。

给出几个可直接使用的例子：

告知用户：每条计划和每天、每周、每月、每季度、每年及自定义周期都可以补充备注、完成反馈和原因，这些内容会随计划保存在远端，换 Agent 仍可读取。可以说“给这项计划补充原因”“记录今天的完成感受”“给本季度复盘补一条说明”。不强迫逐项填写；不保存的内容尊重用户选择。

- “这半年我想完成一个作品，帮我拆到本周。”
- “看看今天的计划，结合日历找出两个小时做重要事项。”
- “每两天练习一次，从下周一开始，先安排晚上。”
- “这个任务延期到周五，原因是等同伴反馈。”
- “这件事今天做完了，但没有记具体时间。”
- “复盘上周，分别看原始期限和调整后的完成情况。”

说明只保存用户愿意保留的内容；演示和讨论不自动落库。Git 普通删除保留历史，日历/通知另有副本，不能承诺彻底忘记。

## 可选：向 Atlas 提炼个人资料

开场中简短告知这项能力，例如：

> 如果你使用 Atlas，我也可以建议把长期目标、重要决策、已确认的成果和明确表达的安排偏好提炼成个人资料，帮助 Atlas 更了解你。重复安排只代表计划，实际习惯需要执行依据。这里先给你看建议内容，由你决定是否交给 Atlas；不会自动同步，也不影响正常使用计划功能。

已有具体计划时，可顺带给出一项有来源的候选；没有时只介绍类别，不为此增加问卷或读取 Atlas。用户暂不需要就继续 onboarding，不将 Atlas 接入列为完成条件，不新增同步配置或进度字段。后续用户明确提及时，按 SKILL.md 的“向 Atlas 提炼数据的提议”给出具体提案。

## 第一轮：最少连接信息

复用当前明确配置；仅缺失时收集：

1. 共享仓库地址和可选分支。无需空仓库，不能把代码分发仓库当个人数据默认目标。
2. 用户时区（如 Asia/Shanghai），以及希望使用的日历服务/日历。地区工作日规则仅在需要时确认地区和年份，不由语言猜国籍。
3. 当前想先处理的一个目标或几条计划。连接未就绪时允许先讨论，明确还没远端保存，不建立本地待同步库。

在宿主工具中发现 Git 和日历能力。已有授权够用不再索取 PAT。日历服务可选用户实际使用的 Google、飞书、Apple/CalDAV 等；不承诺所有宿主都具备适配器。纯 ICS 导出不算已连接。

## 核验与初始化

- 读取仓库身份、默认/指定分支、HEAD 和 plans/ 清单。权限不足/404/截断不证明不存在。
- plans/ 有效则复用；缺失/空目录且用户同意建库则准备 init；文件占位或不兼容内容停止覆盖。其他目录保留。
- 核对多文件原子提交、非强制并发保护和回读能力。辅助脚本返回 prepared 后由现有工具发布，再读 vault、索引和 operation_id。首次 init 回读校验 vault ID 与固定提交。
- 日历核对所选 calendar_id、时区、读取忙闲/事件和写入能力，默认只管理用户选择的专用计划日历，不添加参会人。新建日历也必须在用户请求/接受的配置范围内。
- 日历尚不可用时允许 init calendar.mode=pending，进度 stage=calendar_pending。报告“计划可保存，日历未接入”，不能把 onboarding 整体标为完成。实际回读成功后 configure calendar，记录 provider/calendar_id/verified_at（无凭据）。

## 第二轮：排程习惯与第一条计划

根据需要逐项确认，不发长问卷：可用时段、休息限制/缓冲、是否希望自动建议时间、周起始日、重复任务适用日历。未知先保留，不编造每天可工作八小时等假设。

选一个真实目标：明确想达到什么、当前阶段、约束和下一步；没有长期目标也可先录单条待办。用户不填优先级时 Agent 给有依据的暂定四象限。保留原话/别名与来源引用。先保存，再读取验证；日历时间块也逐一回读。演示一次查询、备注或完成/延期，让用户知道后续怎么说即可。

长期目标与未排程任务允许无 due_at。窗口“晚上”存 time_window；选择具体开始结束后才写 schedule/外部日历。对重复计划确认锚点、周期、本次/以后范围；“每两天”不是“完成后两天”，见 recurrence.md。

## 第三轮：默认定时提醒与报告

主动告知用户可以通过定时任务进行计划提醒，默认每天本地时间 08:00 提醒已有计划并设立或补充当日计划、21:00 给出计划完成情况报告，可单独关闭、修改时间或渠道。这是公开的默认时间，不称为用户指定时间。说明配置保存在远端便于换 Agent 接续，真实触达仍依赖宿主调度器及已授权的本人渠道；缺能力就标记待接入，不承诺已生效。

复用已确认时区与本人渠道，确认安静时段和每日上限。用户接受已告知的 onboarding 默认设置后，用 configure cronjob-defaults 保存两个默认任务及 consent_reference。用户提前关闭某一项时，先用 cronjob 保存该项 enabled=false，再补齐其他缺失默认项；不要先开启再关闭。已有配置不覆盖、不重新开启已关闭任务。缺本人渠道授权时继续普通计划，不把沉默当成授权。

读取 [cronjobs.md](cronjobs.md) 完成配置回读、核查旧执行器、宿主创建或复用并回读、绑定回写。没有持续运行能力时保留待接入配置；用户选择且工具支持时仍可使用日历原生通知。每周复盘、每月目标检查只提议，不默认创建。

单条计划的精确提醒继续用 configure reminders 策略和 notification intent；周期查提醒的 cronjob 通过现有机制去重。宿主调度器和绑定实际回读后才能报告已接入，真实触达另行验收。测试通知本身也须用户授权。用户只想本地试用，不强迫完成真实账号接入。

## 远端进度

plans/policies/onboarding.json 用 configure onboarding 更新：stage、completed_steps、reminders_enabled。阶段建议 repository_pending → calendar_pending → first_plan → ready。ready 需要资料库远端回读、日历实际验证和第一条计划闭环；提醒可选择不开启，不把它设为 ready 的强制条件。

其他偏好若未进入当前 schema，不私自扩展根字段；暂存获准的普通备注或用户未来明确要求扩展。停止或跳过后从远端进度与计划记录续办，不依赖本地缓存或聊天记忆。
