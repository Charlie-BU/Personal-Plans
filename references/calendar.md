# Calendar：排程、同步和外部变更

Calendar 必须被发现并进入 onboarding。用用户实际选择的日历和宿主已有工具，不绑定某品牌、不自写远端客户端。调用外部能力时按宿主要求读取对应已安装日历技能。没有工具或权限应说清缺口；ICS 文本生成不等于已接入。

## 时间安排流程

1. 固定 Git 快照读 agenda、任务和相关长期目标。
2. 从获授权日历读取同一日期范围忙闲和现有事件，核对时区、分页与重复例外。不把取到的第一页当全天全部安排。
3. 用户给了具体时间则检查冲突；“今晚”等窗口先保留原意，再依据容量、依赖、预计耗时给可调整时间块。说明未估时事项，不假定每天八小时可用。
4. 在用户请求/已接受的安排范围内保存 schedule；准备专用计划日历的动作。普通计划写入不授权邀请其他人或修改他人会议。
5. 同步后实际回读事件的 ID、开始/结束与时区，再记录回执。Git 保存、日历同步和提醒触达分别报告。

任务事实、状态和期限以 plans/ 为准；已有会议忙闲以日历为准。默认只管理用户选定的计划日历，不把所有外部会议复制为任务。多次计划可有多个 time block，但当前记录只有一个 schedule；需要多块时拆成子任务/明确实例，不覆盖已有安排。

## 意图与回执

`integration` request 示意：

```json
{"operation_id":"op_calendar_unique","base_commit":"固定仓库HEAD","kind":"calendar","record_id":"已落库任务或实例ID","action":"upsert","payload":{}}
```

先具备 verified calendar 配置。虚拟实例先 materialize，纯窗口不创建无精确时间的会议；日期型 schedule 可创建全天事件。脚本只存 queued 意图，不调用日历。意图固定 record_id/revision/action/payload，执行器读取最新原文构造实际事件。

执行器为每条计划保存/查找稳定 UID（资料库身份 + record ID）和外部 event ID，更新前检查服务版本/ETag（若工具支持）。不同 revision 的 upsert 仍应更新同一计划事件，不每次新建。提供者没有可靠去重/查找能力时，未知结果停止自动重试。

实际回读后，仍用 integration，传 kind、record_id、原 intent_id 和 receipt：

```json
{"state":"confirmed","external_id":"实际事件ID","verified_at":"真实回读时刻"}
```

还支持 unknown/failed；保留原意图标识。即使记录已新增备注、revision 前进，也可以用 intent_id 登记原动作结果；回执不代表最新版本已同步，仍需核对 stale_record_revision。receipt 的 provider ID 是引用，不含认证。

## 外部日历修改

用户在日历拖动事件时读取新事件并比较计划版本：说明差异，按用户此前明确的同步偏好处理。没有偏好时询问是否同步为计划改期。变更 schedule 不自动改变 due_at；截止时间与时间块分开。双方都变更时保留差异，不简单用最后写入胜出。

Git 与日历没有分布式事务。先保存事实/意图，再执行日历，再回写回执；失败时说明“计划已保存，日历未确认”。不能用删除 Git 记录回滚已发送的日历邀请。任务取消/完成时检查未来时间块和通知的处理偏好；不能只更新计划便声称外部事件已撤销。

第一版不自动批量维护无限重复事件；按有限窗口将已选择实例映射为稳定事件，保留系列语义在 plans/，兼容复杂地区日期。ICS 仅导出当前窗口快照，provider是否支持提醒/完成状态需实际核验。
